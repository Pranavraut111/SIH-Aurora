# AURORA — Antarctic Research Station Digital Twin

A physics-informed, AI-assisted digital twin for monitoring, predicting, diagnosing, and supporting operational decisions in remote Antarctic research stations.

---

## SECTION 1 — START HERE

Welcome to the Aurora project! If you are new to the team, start here.

**What is Aurora?**
Imagine a research station in Antarctica where you cannot easily send an engineer every time a generator behaves strangely. The environment is harsh, resources are limited, and failures can be life-threatening. Aurora creates a *digital representation* (a twin) of the station. It estimates what should be happening using physics and compares that against current model-derived or simulated equipment behavior. It then predicts what might happen next (using both foundation AI models and physics), identifies risks, and gives the human operator an evidence-backed explanation.

**What Aurora is NOT:**
- It is not just a dashboard displaying raw data. 
- It is not a generic machine learning model trained on random CSVs.
- It is not a fully autonomous control system (it keeps a human in the loop).

**Who uses it:**
Remote operators, station commanders, and maintenance engineers who need to monitor station health, anticipate failures before they become critical, and make decisions about resource management (e.g., fuel usage, heating, load shedding).

**Why it matters:**
In Antarctica, you can't order spare parts on Amazon. If a generator degrades, you need to know exactly how much time you have before it fails, whether it's caused by the weather or a mechanical fault, and what the safest mitigation is.

**What makes it a Digital Twin rather than just a dashboard:**
A standard dashboard just says "Generator temperature is 85°C." As an illustrative example, Aurora might instead say: "Generator temperature is 85°C, but based on current weather and load, the physics model expects it to be 70°C. This is a severe anomaly. Forecasts show it will hit critical failure (95°C) in 2 hours. Recommendation: Shed non-essential load."

## SECTION 2 — THE CORE IDEA

Aurora’s philosophy is built on causality and evidence. We don't just throw data at a neural network and hope it finds patterns. We build a structured pipeline.

**Conceptual Pipeline:**

```text
Environment (Open-Meteo ERA5 Reanalysis)
    ↓
Physics Digital Twin (StationPhysicsModel)
    ↓
Expected Equipment Behavior
    ↓
Telemetry (Model-Derived)
    ↓
Physics Residuals (Observed - Expected)
    ↓
Anomaly Detection (Isolation Forest)
    ↓
Forecasting (Chronos-Bolt + Physics Forecasting)
    ↓
[PLANNED / NEXT] Forecast Divergence (Comparison)
    ↓
Risk / Decision Engine (Rules + Causal Impact)
    ↓
Grounded Explanation (Groq LLM)
    ↓
Human Operator (React UI)
```

- **Environment**: Input (Weather: temp, wind, pressure). Real [REANALYSIS] data. `weather_data.py`.
- **Physics Digital Twin**: Input (Weather), Output (Expected heat loss, power demand, etc.). A causal engineering model. `physics_model.py`. [MODEL-DERIVED].
- **Telemetry**: The "sensor" readings. In our current state, these are generated by the physics model (with optional synthetic degradation). [MODEL-DERIVED] / [SIMULATED].
- **Physics Residuals**: The difference between what the physics twin expects and what the "sensors" say.
- **Anomaly Detection**: Input (Residuals + Temporal features), Output (Anomaly Score). `anomaly_engine.py`.
- **Forecasting**: Input (Historical telemetry or weather forecast), Output (Future trajectory). Handled by `chronos_forecaster.py` and `forecast_engine.py`.
- **[PLANNED / NEXT] Forecast Divergence**: Comparing the statistical foundation model against the causal physics model.
- **Decision Engine**: Input (Anomalies + Forecasts), Output (Risk level, Recommended Action). `decision_engine.py`.
- **Grounded Explanation**: Input (Structured evidence from Decision Engine), Output (Human readable text). Translated via Groq API in `simulator.py`. [GENERATED TEXT].

    L[Groq API]

**Communication Paths:**
- **Frontend ↔ Backend**: The frontend fetches initial state via REST, but primarily listens to a high-frequency WebSocket (`/ws/station`) for real-time telemetry updates.
- **Backend ↔ Python Simulator**: The Python simulator pushes telemetry batches to the Java backend (`POST /api/sensors/batch`). The backend then broadcasts this to the frontend.
- **Frontend ↔ Python Simulator (Direct)**: The frontend interacts directly with the Python Flask API for complex AI queries (e.g., `/api/aurora-explain`, `/api/anomaly`, `/api/chronos-forecast`) to avoid proxying heavy/blocking ML tasks through the Java backend.

## SECTION 5 — COMPLETE DATA FLOW

**Trace of a single telemetry point (e.g., Generator Temperature):**

1. **Weather**: `weather_data.py` pulls ERA5 data for Maitri (e.g., -25°C, 20km/h wind).
2. **Physics Model**: `physics_model.py` receives weather, calculates building heat loss, determines heating demand, translates to electrical power demand, calculates generator load (e.g., 40%), and derives a nominal generator temperature (e.g., 62°C).
3. **Degradation (Optional)**: `simulator.py` checks if an active failure scenario is injected. If a cooling failure is active, it synthetically adds +5°C to the generator temperature (now 67°C).
4. **Telemetry Batch**: `simulator.py` packages this 67°C reading (along with 30+ other sensors) and POSTs it to the Java backend.
5. **Backend + WebSocket**: Java receives it, saves it (if configured), and broadcasts it via WebSocket.
6. **Frontend**: React receives the WS message and updates the 3D model, sparklines, and gauges.
7. **Anomaly Detection**: Concurrently, `anomaly_engine.py` compares the 67°C reading against the *expected* 62°C reading. It generates a "residual" of +5°C, feeds it to the Isolation Forest, and outputs an anomaly score.
8. **Forecasting**: `chronos_forecaster.py` appends 67°C to its history buffer. Every few minutes, it predicts the next 1 hour of temperatures.
9. **Decision/Explanation**: If the anomaly score is high, `decision_engine.py` compiles the evidence. The user clicks "Explain" in the UI, which sends the structured JSON evidence to Groq (`simulator.py` -> `/api/aurora-explain`), returning a human-readable explanation to the React UI.

## SECTION 6 — STATIONS

Aurora currently supports two isolated Antarctic stations:
- **MAITRI** (70.77°S, 11.73°E)
- **BHARATI** (69.41°S, 76.19°E)

**Station Isolation is a CRITICAL design principle.**
State for Maitri must NEVER contaminate Bharati.
- **Simulator State**: Handled by maintaining separate instances of `StationSimulator` inside `simulator.py`.
- **AI State**: `anomaly_engine.py` loads separate `.pkl` models (`anomaly_model_maitri.pkl`, `anomaly_model_bharati.pkl`). `chronos_forecaster.py` maintains separate `HistoryBuffer` instances per station, though it shares the same stateless PyTorch model weights in memory.
- **Frontend/Backend**: WebSocket messages include a `stationId`. The React context filters incoming messages so the UI only displays the currently selected station.

*Validation*: We have specific tests (`test_chronos.py`, `test_forecast_validation.py`) that verify injecting a severe anomaly in Maitri produces zero mathematical effect on Bharati's predictions.

## SECTION 7 — ENVIRONMENTAL DATA

We pull:
- `temperature_2m` (Ambient Temp)
- `wind_speed_10m`
- `surface_pressure`
- `relative_humidity_2m`

**What ERA5 is:** ERA5 is a global atmospheric reanalysis dataset combining observations with model-based assimilation.
**What ERA5 is NOT:** It is not a real-time sensor strapped to the roof of the Maitri station. 

**Terminology Rules (CRITICAL FOR SCIENTIFIC CREDIBILITY):**
- [REANALYSIS]: The weather data.
- [MODEL-DERIVED]: The equipment telemetry (generator temp, load, etc.). We calculate this using physics.
- [SIMULATED]: When we inject a failure (e.g., "add +10°C to simulate a broken pipe").
- [REAL]: We currently do *not* have direct hardware sensor feeds from Antarctica. Do not claim we do.

## SECTION 8 — PHYSICS DIGITAL TWIN

Implemented in `simulator/physics_model.py`.

The physics model calculates how the station equipment *should* behave based on the environment. 

**Causal Chain:**
1. Outdoor temperature & wind → Building envelope heat loss (Watts)
2. Heat loss → Heating system thermal demand
3. Thermal demand + Base electrical load → Total electrical power demand (kW)
4. Power demand → Generator load (%)
5. Generator load → Fuel consumption rate (L/hr) & Generator operating temperature (°C)

**Parameters:**
Parameters in the code are strictly categorized:
- *Documented*: Based on public specs (e.g., Maitri established 1989, occupants 25).
- *Estimated*: Engineering approximations (e.g., Building U-values).
- *Assumed*: Prototype placeholders (e.g., specific thermostat logic).

**Invariant Tests**: We have tests (`test_physics_invariants.py`) ensuring that if temperature drops, heat demand strictly increases, and generator load strictly increases.

## SECTION 10 — ANOMALY DETECTION

Implemented in `simulator/anomaly_engine.py` (v2).

**Architecture:**
We use a Scikit-learn **Isolation Forest**. 
Crucially, it is trained on *normal data only* (unsupervised).

**Features:**
Instead of just looking at raw temperatures, we use 19 advanced features:
- **Physics Residuals**: `observed_temp - expected_physics_temp`. (This is our most powerful feature).
- **Temporal Rates**: 5-minute and 15-minute rates of change.
- **Correlations**: Rolling correlation between load and temperature.

**Status:**
- It outputs an `anomaly_score` between 0.0 and 1.0.
- A threshold (currently ~0.45) triggers an alert.
- **Cause classification** is currently [PARTIAL] / [EXPERIMENTAL]. It uses a rule-based fallback to guess the root cause (e.g., if residual is high but load is normal -> cooling degradation).

**Limitations**: 
- False positives occur during sudden weather spikes. 
- Synthetic degradation is easy to detect; real gradual wear is harder.

## SECTION 11 — FORECASTING

Aurora uses three distinct forecasting paradigms to provide a complete picture:

**A. Exponential Smoothing Baseline** (`ai_service.py` / `HoltBaseline`)
A simple Holt's linear trend model. Fast, lightweight, purely statistical. Used to prove our advanced models actually add value.

**B. Physics Forecast** (`forecast_engine.py`)
Takes the Open-Meteo weather *forecast* for the next 24 hours and runs it through the `StationPhysicsModel`. 
*Intended for causal forward planning using weather forecasts.*

**C. Chronos-Bolt** (`chronos_forecaster.py`)
A pretrained foundation model for time-series.
*Evaluated for short-horizon statistical forecasting.*

---

## SECTION 12 — CHRONOS

**This is a major technical differentiator.**
Implemented in `simulator/chronos_forecaster.py`.

- **Model**: `amazon/chronos-bolt-small` [PRETRAINED MODEL]
- **Parameters**: 48M.
- **Package**: `chronos-forecasting==2.3.2`, PyTorch.
- **Implementation**: Zero-shot (no fine tuning). 
- **Context Length**: We feed it up to 512 historical 1-minute observations.
- **Prediction Length**: Native limit is ~64 steps (minutes). We use it primarily for +1h forecasting.
- **Output**: Quantile forecasts (p10, p50, p90) providing built-in uncertainty bounds.

It is isolated per station via separate history buffers. Inference runs on a background thread to prevent blocking the main simulator tick loop. Results are fetched by the frontend polling `/api/chronos-forecast`.

## SECTION 13 — FORECAST ARENA

Implemented in `simulator/forecast_arena.py`. 
This is our scientific validation environment for comparing forecasting approaches under the current simulated evaluation setup.

**Methodology:** Walk-forward evaluation across 3,000 simulated minutes. 49 evaluation points. Compares Baseline vs Physics vs Chronos.

**Results (What it DOES demonstrate):**
- **At +1h, Chronos-Bolt achieved lower MAE than the exponential-smoothing baseline across all six station/signal combinations tested. The comparison against the current Arena physics column is not treated as evidence because that column was a noise-based approximation rather than a genuine forward physics forecast.**
- **Uncertainty**: Chronos p10-p90 coverage averaged 82% (target was 80%). Coverage is close to nominal.
- **Divergence**: The Baseline degrades catastrophically at +24h.

**Limitations (What it DOES NOT demonstrate):**
- It does NOT prove real-world Antarctic forecasting accuracy (it evaluated simulated telemetry).
- The "Physics Forecast" in the arena was a *noise-based approximation* (adding Gaussian noise to ground truth), NOT a genuine forward execution of the causal model. Therefore, the long-term physics MAE numbers reflect hand-chosen noise parameters, not empirical proof of physics forecasting accuracy.
- Chronos was not evaluated beyond its native 64-step length.

## SECTION 16 — CAUSAL REASONING

Aurora relies on a documented causal graph (`DEPENDENCY_GRAPH` in `decision_engine.py` and `src/data/stationData.js`).
Weather → Heating → Power Demand → Generator → Fuel.
This allows us to differentiate between:
- "The generator is hot because the weather is -40°C and heating demand is huge" (Normal, expected by physics).
- "The generator is hot, but weather is mild and load is low" (Anomaly -> likely cooling degradation).

## SECTION 17 — GROQ

Implemented as a call inside `simulator.py` (`/api/aurora-explain`).

**Groq is NOT the AI that detects anomalies or runs physics.**
Groq is the explanation/communication layer. 
We take the structured JSON output of the Decision Engine, pass it to the configured model (currently `openai/gpt-oss-120b`) via the Groq API, and ask it to write a concise, professional SITREP (Situation Report) for the human operator.

**Security**: The `GROQ_API_KEY` is kept in `.env` on the Python backend. The frontend NEVER talks to Groq directly.

## SECTION 23 — TROUBLESHOOTING

- **"Chronos taking forever to load"**: First run downloads ~191MB of model weights to `~/.cache/huggingface`. Let it finish.
- **"Groq Explanation failed"**: Check `.env` in the `simulator` directory. Ensure `GROQ_API_KEY` is valid.
- **"WebSocket disconnected"**: Ensure the Java backend is running on port 8080.
- **"No data on screen"**: Ensure Python `simulator.py` is running and successfully POSTing to `localhost:8080/api/sensors/batch`.
- **"ImportError: No module named torch"**: Make sure you activated the `.venv` inside the `simulator` folder before running `simulator.py`.

## SECTION 35 — KEY TERMINOLOGY

- **ERA5**: A global climate reanalysis dataset. Highly accurate historical weather.
- **Model-Derived**: Data generated by math equations, not physical sensors.
- **Physics Residual**: Observed Value MINUS Physics Expected Value. 
- **Isolation Forest**: Anomaly detection algorithm that isolates outliers rather than profiling normal data.
- **Chronos-Bolt**: Amazon's pretrained foundation model for time-series forecasting.
- **Quantile Forecast**: A probabilistic forecast represented by quantiles such as p10, p50, and p90, providing an uncertainty range.
